# Data Dictionary — Churn Feature Pipeline

Status: generated by Claude in Stage 0 from the raw files, then reviewed and corrected by
me. Figures I have not re-checked myself are listed under "Low-confidence items" at the end.

## Overview

The data is an e-commerce customer base of 1,500 customers, with transactions from February
2024 to July 2026. The business meaning of the columns is inferred from their names and
values; no business document was provided.

| Source | Format | Grain | Rows | Customers | Date range |
|--------|--------|-------|------|-----------|------------|
| `data/customers.csv` | CSV | one row per customer | 1,500 | 1,500 | signups 2024-02-14 to 2026-07-01 |
| `data/transactions.db` | SQLite, table `transactions` | one row per transaction | 11,742 | 1,419 | 2024-02-29 to 2026-07-31 |
| `data/transactions_monthly_agg.parquet` | Parquet | one row per customer and calendar month | 8,086 | 1,409 | 2024-02 to 2026-07 |

- `churned` is the label. It must never be used as a feature input.

## 2. `data/transactions.db` — transaction log (row level)

One table, `transactions`. One row per transaction. This is the complete transaction record
and the source for every transaction feature.

| Field | Type | Description | Values / range | Nulls |
|-------|------|-------------|----------------|-------|
| `customer_id` | int | Links to `customers.customer_id` | 2 to 1500, 1,419 distinct | 0 |
| `txn_timestamp` | text, ISO-8601 | Date and time of the transaction, stored as text with sub-second precision. Convert with `pd.to_datetime()` after reading. | 2024-02-29 to 2026-07-31 | 0 |
| `category` | string | Product category | `apparel`, `beauty`, `electronics`, `grocery`, `home`, `sports` | 0 |
| `channel` | string | Where the purchase was made | `mobile_app`, `store`, `web` | 0 |
| `amount` | real | Transaction amount | 3.00 to 1,684.21 per row; mean 49.72, median 33.82 | 0 |
| `is_returned` | int (0/1) | 1 if the transaction was returned (591 rows, 5.0%), else 0 (11,151 rows) | 0, 1 | 0 |

Notes:
- `is_returned` is read as "this purchase was later returned". It is not documented, so this
  is an interpretation. Spend features leave out rows with `is_returned = 1`; transaction
  counts include all rows.
- `amount` is strongly right-skewed (skew 6.11). The mean (49.72) is well above the median
  (33.82), and the largest amount (1,684.21) is about 50 times the median, so a small number
  of large transactions pull the totals up. Spend features should be read with this in mind.
  The highest per-customer average amount is 286.36.
- No transaction is dated before the customer's `signup_date` (0 rows).
- No duplicate rows (0).
- Per customer: 1 to 32 transactions, total spend 4.29 to 1,883.86, 0 to 5 returns.

## 3. `data/transactions_monthly_agg.parquet` — monthly aggregate

The same transaction signal, already aggregated to customer and calendar month.

| Field | Type | Description | Values / range | Nulls |
|-------|------|-------------|----------------|-------|
| `customer_id` | int | Links to `customers.customer_id` | 2 to 1500, 1,409 distinct | 0 |
| `txn_month` | datetime | Calendar month, stored as the first day of the month | 2024-02-01 to 2026-07-01 | 0 |
| `txn_count` | int | Transactions in that month | 1 to 6 | 0 |
| `total_amount` | float | Total amount in that month | 3.00 to 1,753.23 | 0 |
| `return_count` | int | Returns in that month | 0 to 3 | 0 |

There are no duplicate customer-month rows.

**This file is not a complete aggregate of `transactions.db` and must not be used for
features.** I rebuilt the same table from `transactions.db` (customer, month, transaction
count, total amount, return count) and compared the two:

| Comparison | Result |
|------------|--------|
| Customer-months rebuilt from `transactions.db` | 8,188 |
| Customer-months in the parquet | 8,086 |
| Customer-months in `transactions.db` but missing from the parquet | 102, all in July 2026 |
| Customer-months in the parquet but not in `transactions.db` | 0 |
| Customer-months present in both where the numbers differ | 110, all in July 2026 (count and amount differ in all 110; return count differs in 5) |
| Transactions in `transactions.db` | 11,742 |
| Transactions counted in the parquet | 11,505 (237 fewer, about 2%) |
| Customers with transactions in `transactions.db` but no rows in the parquet | 10 |

What this means: the parquet is behind the transaction table for July 2026 only. Every
difference is in that month: 102 customer-months are missing and 110 more have different
counts and amounts. For months up to June 2026 the two sources agree. July 2026 is the most
recent month, and that is the month that matters most for features calculated at
`as_of = 2026-08-01`, so any recent-activity feature built from the parquet would
undercount.

## Time dimensions

- `signup_date` is a date. `txn_timestamp` is a full timestamp. `txn_month` is a calendar
  month.
- The row-level table and the monthly aggregate are two views of the same signal at
  different grains. They agree up to June 2026 and do not agree for July 2026, the latest
  month (see section 3).
- Features are calculated as of a date, `as_of`, that is passed in as a parameter. Only
  transactions with `txn_timestamp < as_of` are used. For training, `as_of` is 2026-05-03,
  90 days before 2026-08-01 (see the note on `churned` in section 1).
- At the training `as_of`, 1,400 customers had signed up (churn rate 11.1%) and 230 of them
  had no transaction yet.

## Data rules for the pipeline

1. `churned` is the label and is never a feature input.
2. Nothing on or after `as_of` is used.
3. Customers with no transaction before `as_of` must get an explicit default value for
   every feature, never null or NaN. There are 81 with no transactions at all, and 230 with
   none before the training `as_of`.
4. All transaction features come from `transactions.db`. Any aggregation that is needed is
   rebuilt from it. The parquet is not used for feature values.
5. `txn_timestamp` is text in SQLite and must be converted to a datetime after reading.
6. The raw files are not edited.

## What I corrected from the Stage 0 version

- The amount figures contradicted each other: the row-level range was given as 3.00 to
  208.38, but the per-customer average was given as up to 286.36, and an average cannot be
  higher than the largest value. I checked the data: the largest single amount is 1,684.21,
  so the 208.38 figure was wrong. The per-customer average of up to 286.36 was correct.
- The `txn_count` range was left as "1 – ???". It is 1 to 6.
- Removed "91 customers have monthly records but no raw transactions". No customer is in the
  parquet without being in `transactions.db`. 91 is the number of customers with no rows in
  the parquet (1,500 minus 1,409).
- The gap between the two transaction sources was mentioned as "possible" and not checked. I
  rebuilt the aggregate and found the parquet is missing 102 customer-months and differs in
  110 more, all of them in July 2026 (section 3).
- Replaced approximate counts ("~81", "~10") with exact ones.
- Added the missing parts: nulls per column, the skew of `amount`, time dimensions, the note
  that there is no churn date, and the list of low-confidence items.
